理解一个设计，需要同时能回答：“它解决了什么问题？还有什么选择？当前选择引入了什么新责任？什么证据会促使重新选择？”不能从 A／B 的名字或频率反推一条已经证明的优化故事。

## 1. 决策总览

| 决策 | 当前结构 | 主要替代方向 | 最值得回答的追问 |
|---|---|---|---|
| D01 流水边界 | A 五级；B 多 BUFFER，读返回寄存化 | 保持五级优化组合路径；重新切级 | 多一级究竟让哪条路径变短？ |
| D02 取指寄存位置 | A 在 ROM 输出；B 在 if_id | 同步 ROM 配套完整取指响应控制 | 为什么换 ROM 不一定多一级？ |
| D03 操作数旁路位置 | EX 等多级结果送 ID | EX 输入旁路；分支与 store 分设旁路 | 前递为何也可能成为时序瓶颈？ |
| D04 load 依赖处理 | 冲刷消费者并重取 | 保持前端、插泡并按就绪放行 | 为什么不直接套教材一拍暂停？ |
| D05 预测复杂度 | A 组合预测；B Bimodal | 无预测／简单静态预测；更严格的组合预测 | 复杂度花在哪里，凭什么值得？ |
| D06 预测元数据 | 固定延迟方向；B 延迟训练 | 随指令携带方向、目标、索引、有效位 | 更深流水怎样避免训练错对象？ |
| D07 访存写缓冲 | 单项待写寄存与同址旁路 | 直接写；有握手的多项队列 | 为什么这还不是通用 store queue？ |
| D08 部分写入 | SB／SH 读改整字再写 | BRAM byte write enable | 只写一个字节为何也依赖读返回？ |
| D09 系统与资源边界 | 固定窗口、BRAM、MMIO、不同频率域 | 统一地址契约、背压协议、CDC 处理 | CPU 正确为何还不等于 SoC 正确？ |
| D10 优化证据 | 保存有历史实现报告，缺同条件性能归因 | 完整约束＋功能基线＋单变量比较 | 主频升高为什么不能直接当提速结论？ |

下面每项都分别标明结构事实、选择理由、代价和验证条件。方案间没有脱离工作负载、时钟与资源约束的永久排名。

## 2. D01：五级还是六级——先找寄存器两侧的组合路径

**要解决的问题。** 同步电路每拍可用时间有限。BRAM 返回之后，若还串联读源选择、同址旁路、load 扩展和写回寄存器输入，就可能无法在目标时钟下稳定采样。五级只是逻辑组织，不保证每一级延迟均衡。

**当前事实（S／H）。** A 为 IF／ID／EX／MEM／WB。B 在 EX 后增加 BUFFER，MEM_BUFFER 保存指令控制与数据，同时 mem_wr_buffer 的 rd_data_o 改为时钟沿寄存；返回数据寄存器与指令控制寄存器是两条配套路径。B 历史关键路径终点落到 rd_data_o 寄存器，A 历史最差路径却在 PC→IROM。它们不是同一条路径的简单前后截屏。依据 [E09](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e09)／[E10](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e10)／[E16](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e16)。

| 可选方案 | 可能收益 | 新责任与代价 |
|---|---|---|
| 保持五级，优化映射、选择逻辑、扇出与放置 | 保持 load 延迟和控制规模 | 能否达标取决于真实路径；布线主导时，仅化简布尔逻辑可能收效有限 |
| B 现有方式：加控制边界、寄存返回 | 让返回链在新端点处结束，给后续扩展另一个周期 | 多一级状态、更多前递源、隔一条 load 依赖检测、数据与控制对齐 |
| 在其他位置重新切级 | 可针对新的瓶颈分配时间 | 不能只搬数据，必须同步搬 rd、写使能、地址、分支元数据与有效性 |

**如何从本例理解代价（I）。** [完整案例](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/12-execution-walkthrough.md#operands)中，A 的重取消费者从 WB 读 load，B 从 MEM 读；B 的最后写回晚一拍。如果把独立操作放在 load 后、消费者前，B 又多一种需要检测的依赖距离。新增寄存器改变的是“值何时可用”，不只是图上多一个方框。

**何时换方案（P）。** 先查完整约束下真正限制时钟的路径。若目标时间已满足，而 load 密集工作负载因额外重取变慢，优先考虑更精确的控制或重新分配边界。若返回链仍无法满足目标，则考虑更细的切分，但必须把增加的周期纳入任务时间。

**如何验证。** V02—V07 检查所有依赖距离和读写配对，V11 核对路径，V12 比较相同程序完成时间。不能通过“多了 BUFFER”推导“已经证明全部频率收益来自 BUFFER”。

**复试回答。** “六级的价值在于重新安排寄存边界，给长组合路径分配时间；代价是 load 返回更晚、旁路来源更多、控制对齐更复杂。是否值得，需要同时检查时序和执行周期。”

## 3. D02：同步 ROM 还是异步 ROM——延迟要由整个取指链承担

**要解决的问题。** IF 给出地址后，指令何时稳定、PC 与指令何时作为同一条指令进入 ID？存储 IP 的输出寄存器也属于流水边界。

**当前事实（S）。** A 的 dist_mem_gen_1 输出 registered，if_id 对指令做组合选择、对 PC 寄存；B 的 IROM 是 non_registered、Pipeline_Stages=0、C_HAS_CLK=0，if_id 寄存指令与 PC。A 注释中的 IF2 未参与电路，因此不能把 ROM 延迟再机械叠加成一个有效 IF2。依据 [E03](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e03)／[E04](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e04)。

**为什么这种选择可以成立（I）。** 两版都可以构成一次 IF→ID 的有效交接，但寄存器位于不同模块。A 的 ROM 输出边界与 PC 保存配套；B 将指令边界放在 if_id。异步 ROM 的地址到数据组合路径进入 if_id 的建立时间预算，同步 ROM 的地址路径则必须满足 IP 内部寄存边界。

**替代方案。** 可以选择同步 ROM 并显式记录请求 PC／响应有效性，或保留当前方式优化映射。若在同步 ROM 后又无条件增加一级指令寄存，就必须承认新增了取指延迟，并重做预测元数据、冲刷和响应丢弃逻辑。不能一边说七级，一边仍用原先两拍预测延迟。

**代价。** 寄存器位置改变会影响 reset／flush 时丢弃哪次 ROM 输出；错误路径的读返回可能在 PC 已重定向后才到达。A 已采用延迟 hold 来处理输出选择，未来改动必须连同 PC 对齐检查。

**何时换方案／如何验证。** ROM 容量、资源映射或前端时序需要变化时再选；以固定 PC 序列、分支重定向和复位为输入，逐拍核对 ID 的“指令＋PC”。验收对象是这对身份一致的信息，不是单看 ROM 有数据。见 V01、V08 与[取指边界](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/03-datapath.md)。

**复试回答。** “同步与异步 ROM 决定数据在哪里跨过寄存边界，不能仅根据有时钟端口就增加一级。这个项目 A 把边界放在 ROM 输出，B 放在 if_id。”

<a id="d03"></a>

## 4. D03：前递到 ID 还是 EX——便利与组合路径长度的交换

**要解决的问题。** 年轻指令需要尚未正式写回的值。经典教材常在 EX 的 ALU 输入前设置旁路；本项目主要在 ID 的寄存器读口选择新值。

**当前事实（S）。** A 按 EX→MEM→WB→阵列选择，B 在 EX 与 MEM 之间增加 BUFFER，x0 优先返回 0。EX 的 load 地址被 not_mem 类条件排除。来源 [E05](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e05)／[E08](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e08)。

**当前方式的合理性（I）。** id_ex 一旦采样，就得到这条指令需要的操作数。算术、分支比较、store 写数据都可共享 ID 读口选择，逻辑上较集中。紧邻 ALU 依赖不必等到 GPR 写回。

**代价。** 当前 EX 运算结果还要经旁路选择，赶到下一条的 id_ex 输入；路径可能跨过 ALU、比较控制和 MUX。来源增加也会增加比较／选择规模与扇出。MEM load 的扩展结果前递 ID，同样要满足该边沿的采样要求。

| 方案 | 正确处理还需要什么 |
|---|---|
| 当前 ID 前递 | 保证 ID 采样前值已就绪，按最新生产者优先，并对未就绪 load 阻止放行 |
| EX 输入前递 | 将原 rs1／rs2 身份随指令保存，在 EX 再选值；分支、store 数据各自覆盖，不能只接 ALU A／B |
| 混合旁路 | 明确定义哪些使用点在哪一级，避免两个位置作不一致选择 |

**具体例子。** [完整案例 C26](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/12-execution-walkthrough.md#operands)中，I10 的 store 基址直接来自 I9 的 EX，写数据来自已经写回的 x12。C27 后继 load 取同一个基址时，A 选 MEM，B 选 BUFFER。依赖解决的是每个读口的来源，而不是一句“支持前递”。

**何时换方案（P）。** 若 routed report 显示 EX→ID 旁路链成为关键路径，可以比较迁移选择位置、局部复制控制或优化 MUX；不能在没有路径证据时宣称移动到 EX 必然更快。

**如何验证。** 连续覆盖同一 rd、两个读口各依赖不同生产者、多个来源同命中、store 地址与数据依赖、x0；既检查值，也检查真实选择优先级。见 V01、V05。

**复试回答。** “前递位置决定操作数必须何时准备好。本项目在 ID 读口集中处理，方便分支和 store 共用，但也会形成 EX 运算到 ID 采样的组合路径。”

## 5. D04：冲刷重取还是保持插泡——控制简化不能掩盖正确性遗漏

**要解决的问题。** load 的值还没回来，消费者不能用旧值执行；老 load 又必须继续前进。

**当前事实（S）。** A／B 紧邻依赖时都会设置 jump／hold，清空年轻位置并把 PC 指回消费者；B 还检测 BUFFER 中的 load。A 仅处理命中位 10／01，漏掉 11，这属于覆盖遗漏，不能解释成有益取舍。依据 [E06](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e06)／[E07](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e07)。

**为什么重取可能有吸引力（I）。** 它复用前端重定向与清空路径，避免为这类依赖单独维护多种保持状态。但这里没有原作者动机证据，也没有证明逻辑面积一定更小。

| 方案 | 对消费者的处理 | 应付出的控制责任 |
|---|---|---|
| 当前重取 | 杀掉当前尝试，重新 IF→ID | 重取目标必须正确；老 load 不丢失；预测元数据与新尝试对齐 |
| 保持式 interlock | PC 与 IF/ID 保持，ID/EX 插泡，老指令前进 | 数据已就绪才解除；reset／branch flush 优先；保持指令与预测元数据 |
| 统一 valid／ready 控制 | 每级根据有效性和接收能力推进 | 需要明确每个副作用只发生一次，并处理后端背压与多种延迟 |

**周期差异（I）。** 教材五级在其既定旁路与存储时序下常用一个气泡；本项目单独紧邻 load 的重取推演使消费者 EX 晚两拍。B 的返回更晚，保持式方案也不能默认仍只等一拍，必须以 ID 采样点是否已有正确值为准。

**何时换方案（P）。** 在修复真实依赖覆盖与 x0／有效源过滤后，如果同负载统计显示重复取指占较大周期，再比较保持式控制。对于带可变延迟存储器的扩展，单靠固定延迟重取通常需要更明确的请求／响应协议。

**如何验证。** V02—V04 与 V08：紧邻、隔一条、双源、load→store、rd=0、重叠分支。每次以“老指令不丢、年轻指令不误执行、副作用不重复”为判定，再统计周期。不要直接将所有 hold 改为“保持寄存器”，因为它们当前可能编码的是清空。

**复试回答。** “这里的 hold 要按代码解释，当前 load 冲突走冲刷重取。我会先保证依赖覆盖，再评估用保持与插泡减少重取；这需要同步处理预测信息与副作用。”

## 6. D05：组合预测还是 Bimodal——准确率收益必须付得起硬件成本

**要解决的问题。** 等 EX 判断分支后再决定后继，会使前端浪费机会。预测器用历史猜方向，并用 BTB 提供早期目标。

**当前事实（S）。** A 有 AREA Bimodal、Gshare 风格分量与 CPT；两套 BTB，CPT 本身不是第三套目标表。B 只有 AREA 风格 Bimodal 与一套 BTB。A 的 GBHR 声明为 10 位，实际异或后索引为 6 位；“10 位历史”不等于 1024 项表。依据 [E14](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e14)／[E15](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e15)。

| 可选方案 | 可能适合的情形 | 代价／局限 |
|---|---|---|
| 无预测或先取顺序路径 | 建立容易验证的功能基线、分支不密集任务 | 遇到实际跳转仍需修正；减少表状态不代表零控制罚拍 |
| 简单静态策略 | 希望低状态成本，模式与规则较吻合 | 仍需早期识别与目标来源；不是删掉预测表就自动拥有静态跳转 |
| Bimodal＋BTB | 单个分支多数时候方向稳定，资源／时序敏感 | 学不到不同分支之间的历史相关性，存在冷启动与索引冲突 |
| 组合预测 | 一部分分支由局部频率解释，另一部分受历史相关性影响 | 多份表、索引计算、选择 MUX、训练与历史对齐，必须验证额外准确率是否抵消成本 |

**本例说明什么。** [两轮循环](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/12-execution-walkthrough.md#predictor)里两版都先冷态错一次，再在退出时错一次。A 第二次 GLOBAL 正确，CPT 仍选 AREA；一次比较胜出只让选择计数移动一步。这是理解机制的例子，不是代表性准确率评测。

**何时换方案（P）。** 若简化后时序显著改善、而目标程序预测损失很小，Bimodal 可能合适。若实际任务分支相关性强、预测错误确实占主要损失，且前端仍有时序余量，再评估组合结构。要保持相同 ROM、RAM、流水控制与实现条件，只换预测器，才可能解释因果。

**如何验证。** V09 分开记录方向错误、BTB miss、目标错误、冷态／热态、索引冲突；V12 比较总周期与执行时间。不要用 A/B 全 top 的 LUT 差额当作预测器独立面积，RAM 容量和其他电路也不同。

**复试回答。** “复杂预测器的价值来自降低特定模式的错误率，但查表与选择会占资源和时序。我会在功能和训练对齐正确的前提下，用目标程序判断准确率收益是否值得。”

## 7. D06：固定延迟训练还是随指令携带元数据——流水变动后的核心责任

**要解决的问题。** 分支到了 EX，需要知道它在 IF 当时预测了什么、使用哪个历史／索引、目标是什么；否则可能拿另一条指令的预测来比较或训练。

**当前事实（S）。** 两版都有方向预测延迟链。A 使用 GBHR 的延迟副本计算更新索引；B 把实际分支结果再寄存后更新预测表，但 EX 的实际重定向没有因此延后一拍。条件分支主要比较方向错误，目标错配缺少独立恢复路径。依据 [E13](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e13)／[E14](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e14)。

**当前方式的合理性与边界（I）。** 固定流水、正常推进时，两拍延迟可以实现 IF 与 EX 对齐。加入气泡、保持、重取或更深预测流水后，指令的有效推进与时间经过不再总是一回事；仅记录“过了几拍”可能不足。这个风险需要逐序列验证，不能把所有场景预先断言为已出错。

**候选方式（P）。** 让预测方向、目标、用于查表的历史／索引、有效位与指令 PC 一起经过前端寄存器。到 EX 时比较同一条指令的预测与实际；冲刷时一起失效。若采用推测更新历史，还需明确回滚到哪个检查点；不能只增加一个更长 GBHR 就视作完成。

**代价。** 增加元数据寄存、冲刷控制和索引保存；早训练有较短学习延迟，但必须明确训练是否会被后来杀掉的指令污染。晚训练也不能丢失原分支身份。设计要定义策略，不能让过程执行次序替代策略。

**何时换方案／如何验证。** 修改暂停方式、增加预测级、处理连续分支或扩大地址空间前，应优先将身份契约明确化。V08／V09 用 PC、预测索引、历史、真实方向作逐条配对，并注入错误目标验证恢复。若只看最终程序结果，可能漏掉训练了错误表项却暂时没影响输出的情况。

**复试回答。** “分支训练要关联到当时预测的那一条指令。流水增级或控制变化时，我会让预测元数据随指令保持和冲刷，并分别验证纠错时刻与训练时刻。”

<a id="d07"></a>

## 8. D07：单项写缓冲还是通用队列——先说清存储接口契约

**要解决的问题。** 写请求打一拍后才送出，后继 load 可能在 RAM 提供新值之前就需要同址数据。

**当前事实（S）。** mem_wr_buffer 保存一份地址、数据、写使能，没有请求应答或队满协议；没有新写时使能清零。A 用缓存命中组合前递；B 在时钟沿选择“当前写→缓存写→内存返回”。依据 [E10](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e10)／[E11](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e11)。

**当前方式的合理性（I）。** 在每拍可接收写请求的固定 BRAM 接口下，一份待写寄存可隔离请求边界，同址旁路可避免紧邻读到旧字。但源码注释即使写“FIFO”，也不能据此认定它有多项排队、拥塞处理或提交机制。

| 替代方案 | 可能收益 | 必须补齐的条件 |
|---|---|---|
| 直接将 MEM 写请求送 BRAM | 少一个待写边界 | 重新检查写请求路径、BRAM 同址读写模式与 load 返回对齐 |
| 当前单项缓冲＋旁路 | 适应固定延迟接口，结构有限 | 保证接收吞吐；当前／缓存同时命中时选最新；不能丢写 |
| 有握手的多项写队列 | 允许下游暂时不能接收并容纳多项待写 | 队满背压、按序写出、load 搜索最新匹配、字节覆盖、冲刷与异常策略 |

**本例的具体代价。** [I10→I11](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/12-execution-walkthrough.md#memory)中，A 从待写缓存取 10，B 从当前写请求选择并寄存 10。多出一次读返回寄存后，地址与控制也必须延迟匹配。B posedge 阻塞赋值问题是需要审查的编码风险，不能作为合理的时序优化技巧来宣传。

**何时换方案（P）。** 仅在接口需要可变延迟、连续拥塞或更复杂存储顺序时考虑队列；扩大缓冲深度不是自动提升性能。若只为修复当前正确性，先把现有边沿语义与同址优先级证明清楚。

**如何验证。** V06：连续两次写同一字后读、写不同字后读、当前写与缓存写同时命中，分别使用易区分数据；观察实际 RAM 写端确认每次写恰好发生一次。再扩展下游背压前，必须先定义谁能拒收以及如何保持请求。

**复试回答。** “当前是固定接口上的待写寄存和同址旁路，不能把它当作通用写队列。要支持可变延迟，还需要接收协议、背压和多项最新数据选择。”

<a id="d08"></a>

## 9. D08：读改写还是字节使能——少一组写掩码，多一条旧值依赖

**要解决的问题。** SB／SH 只改变一个字中的部分字节，其他字节必须保留。

**当前事实（S）。** mem 读取旧字，根据地址低位与 funct3 合并 store 数据，再写整字。活动通路没有将普通 byte enable 直接作为 BRAM 的字节写使能完成这件事。依据 [E10](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e10)／[E11](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e11)／[E12](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e12)。

**当前方式的合理性（I）。** 在整字写接口上可以复用返回数据与组合拼接实现部分写。代价是 store 本身也依赖旧字正确返回；不只是 load 才关心返回地址、延迟与同址旁路。

**替代方案（P）。** 若目标 BRAM IP 与工具配置支持，可使用 byte write enable，让地址与写掩码选择要更新的字节。这样能减少对旧字返回的依赖，但要改 IP 配置和贯穿 CPU／桥的控制，重新验证连续部分写与读出效果；不是将一个 mask 信号接上就自然完成。

**例子。** 假设按项目的低字节对应低地址规则，原字为 0x11223344，在地址 +1 执行 SB 写 0xAA，目标字为 0x1122AA44。若旧字来自错误地址或上一轮返回，即使写入的 AA 正确，其余三个字节仍可能被破坏。这是待验证输入与预期，不是已运行结果。

**何时换方案／如何验证。** 部分写频繁、读改写路径成为瓶颈，或正确性维护成本过高时比较 byte enable。V07 覆盖四个字节位置、合法半字位置、连续覆盖和邻字隔离；越界／非对齐行为要明确另行定义，不能从对齐用例推导已支持。

**复试回答。** “读改写适配整字接口，但让 store 增加了旧值依赖。字节使能可以改变这条依赖，需要配套 IP 和写掩码控制，并验证未写字节不变。”

<a id="d09"></a>

## 10. D09：系统契约比功能列表更重要——地址、时钟与背压

**要解决的问题。** 软件看到的是内存和外设行为；CPU 内部算术正确，也可能因为地址别名、请求丢失或跨域状态不一致得到错误结果。

**当前事实（S）。** A RAM 为 64 KiB、B 为 256 KiB，桥名义窗口约 256 KiB；A 有效 word 地址裁到 14 位。CPU 与计数器等使用 PLL 的不同输出频率，存在直接控制／数据连接；A 活动顶层的 rib_hold 固定为 0。依据 [E02](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e02)／[E11](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e11)／[E12](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e12)／[E22](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e22)。

**为什么有限接口能服务项目（I）。** 固定 BRAM、已知地址范围和固定接收能力，可降低总线控制规模，便于运行受控教学程序。但它只在这些前提下成立；“接口上有 hold”不等于下游可变延迟已经被处理。

| 子决策 | 可以选择什么 | 当前应该先弄清的事 |
|---|---|---|
| 地址空间 | 与物理容量一致地限制；显式声明镜像；增加容量 | A 高地址是否别名，窗口终点的比较语义，软件链接脚本是否匹配 |
| 时钟关系 | 相关时钟按关系约束；按实际协议实现捕获；必要时握手或异步 FIFO | 两路来自同一 PLL 不等于所有信号可靠，也不等于必然异步 |
| 快慢域控制 | 拉宽并确认事件；请求／应答；在源域保存多位快照 | 单拍请求是否被接收、多位总线是否一致，不能用逐位两级同步处理所有问题 |
| 存储扩展 | 维持固定接收契约；增加 valid／ready 等协议 | 无背压时哪一级必须保证每拍接收；拒收时指令和副作用怎样保持 |
| 复位 | 明确每个域的释放条件与状态初始化 | PLL locked 如何使用，未复位寄存如何收敛，是否可能产生初始错误请求 |

**何时换方案（P）。** 当程序容量、外设延迟或时钟安排超出受控假设时，应先升级契约与验证，再加功能。扩大 RAM 后，也要检查地址译码、程序布局与资源消耗，而不只是 IP 深度。

**如何验证。** V07 检查高低地址不意外互相覆盖；V10 检查复位与请求计数、多位数据一致性；V11 检查时钟关系及约束覆盖。对未证实风险，报告观察与限制，不将所有跨频率连线直接判成确定故障。

**复试回答。** “SoC 集成的难点是把地址、时钟和请求响应约定贯通。当前固定 BRAM 场景可以较简单，但扩展到慢外设或更大空间前，需要先保证请求不丢和地址不别名。”

<a id="d10"></a>

## 11. D10：如何判断优化值得——频率、周期、面积分别记账

**要解决的问题。** 主频更高可能同时引入更多气泡、使用更多存储资源，甚至还未证明相同程序结果正确。需要能解释任务完成时间的证据。

**已有事实（S／H）。** 配置 CPU 时钟是 A 150 MHz、B 250 MHz；历史 WNS 分别为 +0.865 ns、+0.035 ns。历史 top LUT 为 5482／4448，BRAM tile 为 16／64。两份报告均有 no_clock 等约束覆盖事项。这些数值的版本、条件与来源见 [E02](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e02)／[E16](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e16)／[E17](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e17)／[E18](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/09-evidence.md#e18)。

**能说什么。** B 的配置时钟更高，历史报告在已分析 setup 路径上为正 slack；可以研究相应路径和资源。**不能据此说** B 已在所有程序中加速 250／150 倍、组合预测独占全部 LUT 差额、或正 WNS 证明整机所有路径均满足时序。

评估关系是：

~~~text
相同任务执行时间 = 实际执行周期数 / 实际时钟频率
若有效完成指令数相同：
时间之比 T_B/T_A = (CPI_B/CPI_A) × (f_A/f_B)
~~~

若指令数也改变，应直接比较完整周期与时间；不能只比 CPI。功耗工具估计不是实测板卡功耗，若讨论能耗则还需明确功耗口径与运行时长。

**一个纯假设的决策阈值。** 在相同指令数、同任务、功能正确且频率确为 150／250 MHz 的条件下，B 要更快，需要 CPI_B／CPI_A 小于 250／150，约 1.667。这个式子帮助理解“可容忍多少周期增加”，不表示项目已经测到该 CPI。真实比较还要统一启动／结束与 I/O 计时边界。

**候选评估流程（P）。**

1. 固定源码、IP 初始化、容量、器件、工具、程序和编译条件，先通过功能基线。
2. 修正或解释约束覆盖缺项，检查 setup／hold 与时钟关系。
3. 一次改变一个可隔离变量，例如同一流水内换预测器，记录指令数、周期、误预测、重取、资源和路径。
4. 若不得不同时改动多个结构，明确它是整体方案比较，不把差异归因给单一模块。
5. 比较任务时间与资源是否满足目标，再决定是否保留改动。

**复试回答。** “我会先证明相同任务输出正确，再按周期除以频率比较时间，并结合资源与约束覆盖。现有历史报告支持结构和时序分析，但不足以独立证明某项改造的性能增益。”

可以使用同一答题结构：**问题→源码中的选择→可替代方案→代价→验证依据**。遇到“这是创新吗”，再补上参照对象；成熟机制在项目中的应用价值与原创性是两件需要各自证据的事。

| 追问 | 可先给出的判断 | 深入依据 |
|---|---|---|
| 六级一定比五级好吗？ | 取决于缩短周期时间能否抵消额外延迟／气泡，以及正确性成本 | [D01](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d01)、[D10](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d10) |
| 为什么不把 A 的预测器直接放进 B？ | 可以作为候选，但前端路径、训练元数据和资源都要重新验证 | [D05](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d05)、[D06](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d06) |
| 为什么 load 不只停一拍？ | 要看消费者采样点与返回就绪点；当前重取还要重新经过 IF／ID | [D04](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d04) |
| 为什么旁路会拖慢频率？ | 数据要经过实际运算和选择网络，最终仍受寄存器建立时间约束 | [D03](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d03) |
| 这里有 FIFO 就能接慢存储吗？ | 当前没有拒收／队满协议，不能直接推导能处理背压 | [D07](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d07) |

| 为什么还要研究时钟和地址？ | 软件结果依赖整个 SoC 契约，核内运算正确不足以保证系统正确 | [D09](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/13-architecture-decisions.md#d09) |
| 能证明是谁为什么做了这些选择吗？ | 本章能追溯结构与报告；没有动机／归属证据时，仅给出工程推理 | 本章开头、[历史边界](D:/codex_prj/fpga_dick/jyd-riscv-soc/docs/research/10-history.md) |

示例讲法：“这个版本为了将存储返回链分到更多寄存边界，增加了 BUFFER 和读返回寄存。相应代价是 load 就绪更晚、前递来源更多，并需要处理隔一条的依赖。另一条路线是保留五级优化路径，是否值得要以完整约束下的关键路径和相同程序执行时间判断。当前文档完成的是静态分析，实验验证仍待进行。”
